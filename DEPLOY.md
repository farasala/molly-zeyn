# DEPLOY.md — этап 1: Supabase, GitHub, Vercel, домен

Пошагово. Делайте по порядку, каждый шаг проверяется следующим.
Всё, что здесь есть, — разовая настройка. Дальше деплой идёт сам при каждом `git push`.

---

## 1. Supabase — база и аккаунты

### 1.1 Выполнить схему

1. Откройте свой проект на [supabase.com](https://supabase.com) → **SQL Editor** → **New query**.
2. Скопируйте туда весь файл `schema.sql` из этой папки и нажмите **Run**.
3. Внизу должно быть `Success. No rows returned`. Скрипт можно перезапускать сколько угодно —
   он не ломает уже созданное.
4. Проверьте: **Table Editor** → в списке появились `profiles`, `groups`, `group_members`,
   `activity_results`, `known_words`, `homework`, `homework_submissions`.
   У каждой таблицы стоит зелёная метка **RLS enabled**.

### 1.2 Выключить подтверждение почты

Иначе студент зарегистрируется, но не сможет войти, пока не откроет письмо.

**Authentication** → **Sign In / Providers** → **Email** → выключить **Confirm email** → **Save**.

Если оставить включённым — приложение это переживёт: после регистрации оно скажет
«откройте ссылку из письма», — но тогда в **Authentication → URL Configuration → Site URL**
нужно вписать адрес сайта, иначе ссылка из письма будет вести на `localhost`.

### 1.3 Забрать ключи

**Project Settings** → **API**. Нужны два значения:

| Что копировать | Куда |
|---|---|
| **Project URL** (`https://xxxx.supabase.co`) | `NEXT_PUBLIC_SUPABASE_URL` |
| **anon / public key** | `NEXT_PUBLIC_SUPABASE_ANON_KEY` |
| **service_role key** | `SUPABASE_SERVICE_ROLE_KEY` — понадобится позже, но пусть лежит |

`anon key` попадает в браузер — это нормально, его защищает RLS.
`service_role key` не должен попасть ни в браузер, ни в git. Никогда.

### 1.4 Локальный файл ключей

В папке проекта скопируйте `.env.example` в `.env.local` и подставьте значения.
`.env.local` уже в `.gitignore` — в GitHub он не уедет.

## 2. GitHub — код

1. [github.com/new](https://github.com/new) → имя репозитория `english-studio` → **Private** →
   **без** README, .gitignore и лицензии (они уже есть) → **Create repository**.
2. GitHub покажет адрес вида `https://github.com/ВАШ-ЛОГИН/english-studio.git`.
   Пришлите его мне — я подключу и запушу. Или сами, из папки проекта:

```bash
git remote add origin https://github.com/ВАШ-ЛОГИН/english-studio.git
git push -u origin main
```

При первом пуше Windows откроет окно входа в GitHub — войдите, пароль сохранится.

## 3. Vercel — хостинг

1. [vercel.com/new](https://vercel.com/new) → **Import Git Repository** → выберите `english-studio`.
   Если репозитория нет в списке — **Adjust GitHub App Permissions** и дайте доступ к нему.
2. Framework Preset определится как **Next.js**. Root Directory — `./`. Ничего не меняйте.
3. Разверните **Environment Variables** и добавьте три переменные — те же, что в `.env.local`:

   ```
   NEXT_PUBLIC_SUPABASE_URL
   NEXT_PUBLIC_SUPABASE_ANON_KEY
   SUPABASE_SERVICE_ROLE_KEY
   ```

   Это самая частая причина «локально работает, на сайте нет». Проверьте, что все три на месте
   и без лишних пробелов по краям.
4. **Deploy**. Через 1–2 минуты получите адрес `english-studio-xxxx.vercel.app`. Откройте его —
   должен открыться тёмно-зелёный экран входа.

Дальше каждый `git push` в ветку `main` пересобирает сайт автоматически.

## 4. Домен hoster.kz

Домен на hoster.kz ещё не куплен. Порядок такой:

1. Купите на [hoster.kz](https://hoster.kz) **только домен**. Хостинг не нужен — сайт живёт на Vercel.
2. Vercel → проект → **Settings** → **Domains** → введите домен → **Add**.
   Добавьте обе формы: `example.kz` и `www.example.kz`.
3. Vercel покажет, какие DNS-записи нужны. Обычно это:

   | Тип | Имя | Значение |
   |---|---|---|
   | A | `@` | `76.76.21.21` |
   | CNAME | `www` | `cname.vercel-dns.com` |

   **Сверяйтесь с тем, что показал именно ваш Vercel** — адреса он иногда меняет.
4. Панель hoster.kz → ваш домен → **DNS-записи** (или «Управление зоной») → добавьте эти две
   записи ровно как показал Vercel. Если там уже есть записи `A @` или `CNAME www` от
   парковочной страницы хостера — удалите их, иначе будет конфликт.
5. Ждите. DNS обновляется от 15 минут до нескольких часов. В Vercel у домена статус сменится
   на **Valid Configuration**, HTTPS-сертификат Vercel выпустит сам.
6. Когда домен заработает, вернитесь в Supabase → **Authentication** → **URL Configuration** →
   впишите домен в **Site URL**, а `https://*.vercel.app`-адрес добавьте в **Redirect URLs**.

Адрес `*.vercel.app` продолжает работать всегда — это запасной вход, если с доменом что-то не так.

## 5. Проверка этапа 1

Ровно та, что в `CLAUDE.md`. Не проходит — дальше не идём.

1. Откройте адрес сайта **с телефона**, вкладка **Sign up**.
2. Зарегистрируйтесь: имя, почта, пароль от 6 символов, роль **Student**.
3. Должен открыться дашборд с вашим именем.
4. **На ноутбуке**: Supabase → **Table Editor** → `profiles`. Строка с этим студентом на месте,
   `role` = `student`.
5. На телефоне: меню в правом верхнем углу → **Log out** → войдите снова той же почтой и паролем.
6. Перезагрузите страницу — вы всё ещё внутри. Сессия держится.

Если после регистрации в `profiles` пусто — не выполнен `schema.sql` (шаг 1.1) или не создался
триггер `on_auth_user_created`. Прогоните скрипт заново.

## 6. Что осознанно отложено

- **Роль выбирает сам регистрирующийся.** Так написано в `CLAUDE.md`, так и сделано. Но это
  значит, что любой человек с ссылкой может завести себе аккаунт преподавателя и увидеть
  учеников своей группы. До первых настоящих студентов это надо закрыть — проще всего убрать
  выбор роли из формы и выдавать роль преподавателя вручную в Supabase.
- **Регистрация открыта всем.** Пока платформа не анонсирована — не проблема. Позже стоит
  добавить код приглашения.
- **Бэкапы базы.** На бесплатном плане Supabase их нет. Перед первыми студентами — Supabase Pro.
